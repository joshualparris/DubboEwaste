## Freshness rules

- **Current operation guides** (application, deployment, role/security, software statuses) must agree with the code and connected data **as of their timestamp**. Newer implementation changes require a new review.
- **Dated build reports and feature plans** describe a historical change, *not* necessarily the present deploy. Earlier "not built" or "not deployed" statements might have been superseded; follow the live feature register.
- **Research, expert notes, comparisons and gap investigations** preserve the author's original evidence and dates. Their contents cannot honestly be labelled "100% current" without checking each original source and contacting external stakeholders. Preserve rather than silently revise them.
- **Templates** are drafts: check Australian legal/insurance requirements, names, contact details and consent before real external use.
- **Legacy `DubboEwasteApp/`** documents describe an older static prototype, not `EwasteApp/`.
- **Do not promote source code into operational truth:** a created route, local migration, queued email, source-level mobile QA or a Vercel READY build is not proof of browser behaviour, applied database parity, transmitted emails or approved community events.
- Never seed imaginary venue bookings or volunteers to make a dashboard look complete.
